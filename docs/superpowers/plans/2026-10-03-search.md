# Search 1.8 implementation plan

> Execute inline in the existing checkout, following Oleg's standing authorization to continue the client. No delegation or additional approval round.

**Goal:** Find music while typing, open mixed quick results, and reuse recent searches.

**Architecture:** The existing search screen gains a small controller for debouncing, cancellation and paging. A typed API result preserves server order across music entities. Search history uses the existing account-scoped SQLite state table.

**Tech Stack:** Flutter 3.47.6 / Dart 3.13.5, existing http and sqflite dependencies.

**Spec:** This bounded change follows the design presented in chat: input → category chips → compact results; an empty input shows recent searches. No new dependency, database migration or playback change.

## Constraints

- Keep baseline 10 points, votes, manual order, login and playback queue intact.
- Default “Всё” uses quickSearch with Track/Artist/Release/Playlist fragments; unsupported types are skipped.
- Typing waits 350 ms; two characters trigger automatically; explicit submission allows a single character.
- Edits, category changes, API/account replacement and disposal invalidate pending work immediately.
- Recent searches: 20 unique normalized queries, most recent first, account-scoped; record submission/result selection, never each keystroke. Support individual deletion and clearing.
- Pagination uses existing opaque cursors, deduplicates results, stops on a repeated cursor.
- UI must scroll with keyboard and at 360 dp / 1.6× text, with error/retry and clear-input actions.
- Build signed 1.8.0+11; public release and private mirror. Only install physical device with adb install --no-streaming -r, if connected. Never uninstall it.

## Design check

Search input is the visual focus. Categories use existing choice chips; active selection remains clearly filled. Music uses existing compact rows, preserving artwork and text alignment. History is a separate empty-input state with one quiet header and local deletion controls. Loading is a thin indicator; empty and failure states remain scrollable with large text. No decorative cards or extra persistent panels.
